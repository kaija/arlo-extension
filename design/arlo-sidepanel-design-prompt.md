# Claude Design Prompt — Arlo 側邊欄代理介面

> 使用方式：把「以下全部內容」貼給 Claude Design（或執行 `/design` 並附上本檔）。
> 本 prompt 只描述**功能、狀態與內容**。視覺系統（色彩、字型、圓角、間距、插圖）完全由設計端決定。

---

## 1. 要產出什麼

一張 Claude Design 畫布，包含下列 artboards，呈現一個 Chrome 擴充功能側邊欄的完整互動故事。

- 側邊欄 artboard 尺寸：**400 × 760**（Chrome MV3 side panel 的實際可用寬度）
- 另有 **1 張 1280 × 800** 的 artboard，用來呈現「瀏覽器視窗 + 網頁 + 右側側邊欄」的整體關係
- artboard 依「使用者旅程順序」由左至右排列，並以分組標題分區：Onboarding / 主流程 / 失敗狀態 / 設定 / 深色版

## 2. 產品是什麼

**Arlo** 是一個瀏覽器代理（agentic browser operator），住在 Chrome 側邊欄裡。使用者用自然語言交代一件事，Arlo 會**實際操作使用者眼前這個分頁**——點擊、輸入、捲動、換頁——直到任務完成。

它不是問答助理。它是一個會動手的東西，所以整個介面的核心命題只有一個：

> **使用者必須隨時知道它正要做什麼、已經做了什麼，並且能在它做出無法收回的事之前攔下它。**

## 3. 不可更動的功能條件

1. 介面文案一律**英文**（本文件的中文只是說明，不要出現在畫面上）
2. 面板寬度固定 400px；所有版面必須在這個寬度內成立
3. **淺色與深色兩套主題都要成立**（主要畫面用淺色，另有指定的深色版 artboard）
4. Arlo 操作的是**使用者當下看得見的分頁**，不是背景分頁、不是另開視窗
5. 權限是**安裝時一次取得全域授權**，執行中不會再跳「是否允許此網站」
6. 頁面上的視覺回饋**只有目標元素高亮框**

## 4. 核心概念與詞彙（畫面上要一致使用）

| 概念         | 說明                                                                 |
| ------------ | -------------------------------------------------------------------- |
| **Task**     | 使用者交代的一件事，用自然語言下達                                   |
| **Plan**     | Arlo 提出的編號步驟清單，執行前必須經使用者核准一次                  |
| **Step**     | 計畫中的單一動作，狀態為 pending / running / done / failed / skipped |
| **Gate**     | 執行到不可逆動作前的強制停等確認                                     |
| **Run card** | 對話串中代表一次任務執行的可摺疊卡片                                 |

**不可逆動作**（會觸發 Gate）：送出表單、下單／付款、寄出訊息或郵件、刪除資料、登入、變更帳號設定。
其餘動作（讀取、捲動、點擊導覽連結、搜尋、篩選、開分頁）不需確認，直接執行。

## 5. 狀態機（所有畫面都是這條線上的一點）

```
Idle ──使用者輸入任務──▶ Planning ──▶ Plan awaiting approval
                                              │
                              ┌───核准────────┘
                              ▼
                          Running ──遇到不可逆動作──▶ Gated ──核准──▶ Running
                              │                          └──拒絕──▶ Stopped
                              ├──步驟失敗──▶ Needs help（三種變體，見 §6）
                              └──全部完成──▶ Done
```

使用者在 Running 狀態下必須永遠能 **Pause** 與 **Stop**，且 Stop 之後看得到「已經做了什麼」。

## 6. Artboard 清單與內容

以下每一張都用**同一個劇本**，讓整張畫布串成一個連續故事：

> **劇本**：使用者在一個電商網站上。任務是
> `"Reorder the coffee beans I bought last month, but only if they're still under $25."`
> Arlo 的計畫：開啟訂單頁 → 找出上月訂購的 "Ethiopia Yirgacheffe 1kg" → 確認現價 $23.40 → 加入購物車 → 前往結帳 → **[Gate] 送出訂單 $25.87（含運）** → 回報訂單編號。

### 群組 A — Onboarding（3 張）

**A1. What Arlo does**
安裝後第一畫面。誠實說明它會實際操作網頁，不是聊天機器人。用 2–3 個具體任務例子表達能力邊界。

**A2. Permission request**
要求全域網站存取權。這張是整個產品最重要的信任時刻，內容必須說清楚：

- 它能在你造訪的任何網站上讀取與操作
- 它**永遠**會先給你計畫、且在不可逆動作前停下來
- 你隨時能在設定頁全域關閉
  主要行動為 "Allow Arlo to work on websites"，並提供次要出口。

**A3. Try your first task**
把使用者推進第一個任務，沿用當前網站的情境化建議。

### 群組 B — 主流程（7 張）

**B1. Empty state（Idle）**

- 面板頂部：產品識別 + 新任務 + 設定入口
- 中央：大型任務輸入框
- 輸入框上方：**3–4 個依當前網站而變的範例任務**（此劇本中即為電商相關，例如 `"Reorder something from my past orders"`、`"Compare the top 3 items on this page"`、`"Fill this form with my saved details"`）
- 要能看出「Arlo 知道你現在在哪個網站」

**B2. Planning**
使用者已送出任務、計畫尚未成形的中間狀態。要表達 Arlo 正在讀取當前頁面。這是一個短暫但真實存在的狀態，不要跳過。

**B3. Plan awaiting approval**

- 使用者訊息在上，Arlo 的計畫卡在下
- 編號步驟清單（7 步，如劇本）
- 其中「送出訂單」該步必須**在清單中就被標示為需要確認的動作**，不能等執行到才驚喜
- 行動：Approve and run / Edit plan / Cancel
- 要能表達「這只是計畫，還沒有任何事情發生」

**B4. Running — 收合**
展示長對話中的常態。Run card 收合為精簡列：任務名稱、進度（`Step 4 of 7`）、目前正在做什麼的一行文字、以及 Pause / Stop。使用者不展開也知道現況。

**B5. Running — 展開**
完整步驟清單，同時存在四種步驟狀態：已完成（含簡短結果，例如 `Found: Ethiopia Yirgacheffe 1kg — $23.40`）、進行中、待執行、以及被標記為稍後需要確認的那一步。這張是整份設計的核心，資訊密度最高。

**B6. Gate — 不可逆動作確認**
執行到「送出訂單」時停下。這張畫面的成敗在於**使用者不必回去讀計畫，就能判斷該不該按下去**。必須包含：

- 這一步具體會發生什麼：`Place order — $25.87 total, charged to Visa ending 4821, ships to Home`
- 這是不可逆的
- 行動：Approve / Skip this step / Stop task
- 使用者不回應時任務就停在這裡等，不會自己繼續

**B7. Done**
Run card 收合成一行結果摘要（含訂單編號），下方可繼續追問或下新任務。使用者能展開回看完整步驟。

### 群組 C — 失敗與交棒（3 張）

代理型產品真正的考驗在失敗時。三張都要讓使用者清楚知道：**現在球在誰手上**。

**C1. Element not found / page changed**
Arlo 找不到預期的按鈕。要說明它卡在哪一步、看到了什麼，行動為 Retry / Take over（使用者自己動手後讓它接續）/ Stop。

**C2. Sign-in required**
需要登入才能繼續。Arlo **不會**代填帳密。它交棒給使用者，並在使用者完成登入後可續跑。

**C3. Blocked by CAPTCHA**
Arlo **不解 CAPTCHA**，這是產品原則不是缺陷，畫面要這樣呈現。使用者處理完後恢復執行。

### 群組 D — 設定（1 張）

**D1. Settings**
你選擇了全域授權，所以這頁是使用者唯一的煞車。必須包含：

- 全域總開關（Pause Arlo everywhere）
- 網站封鎖清單（永不在此運作，預設帶入銀行／信箱類網域）
- 哪些動作算「不可逆」而需要確認（可調整的清單）
- 模型與 API key
- 執行歷史的保存與清除

### 群組 E — 頁面上的樣子（1 張，1280 × 800）

**E1. On-page highlight**
完整瀏覽器視窗：左側是一個真實感的電商網頁，右側是側邊欄（顯示 B5 的執行中狀態）。頁面上**正被操作的那個元素有高亮框與簡短標籤**（例如 `Clicking "Add to cart"`）。
不要畫：浮動控制球、步驟截圖、全頁遮罩。

### 群組 F — 深色版（3 張）

淺色版中最關鍵的三張的深色對照：**B5（執行中展開）**、**B6（Gate）**、**B1（空狀態）**。

## 7. 明確不要做的事

- 不要浮動控制球／可拖曳的頁面控制項
- 不要每個步驟的截圖縮圖
- 不要全頁遮罩或聚光燈
- 不要逐網站授權彈窗
- 不要歷史任務列表頁
- 不要把執行過程放進獨立分頁或獨立區塊——它必須內嵌在對話串裡
- 不要在 composer 放模型選擇器（模型設定在設定頁）
- 訊息不要用左右對話泡泡；400px 欄寬應以全寬區塊處理，使用者訊息另以其他方式區分

## 8. 視覺系統：由你決定

本 prompt **不指定**任何色票、字型、圓角、間距尺度、圖示風格或插圖方向。請自行建立一套完整且前後一致的視覺語言，並以此貫穿所有 artboard。

唯一的功能性要求是：使用者必須能**一眼分辨**下列狀態彼此不同——待核准、進行中、需要你確認、已完成、失敗／卡住。至於用什麼手段做到，是你的設計決定。

## 9. 驗收標準

1. 把 B3 → B5 → B6 → B7 四張依序看過，一個沒讀過說明的人能講出 Arlo 剛剛做了什麼、以及他在哪一刻擁有否決權
2. B6 單獨拿出來看，資訊足以做決定，不需回頭查計畫
3. C1–C3 三張都能明確回答「現在該我動手，還是它還在跑？」
4. A2 讀完之後，把整個瀏覽器的操作權交出去這件事，是可以被理解與接受的
5. 所有內容在 400px 寬度內成立，沒有橫向溢出、沒有靠縮小字級硬塞
6. 深色版三張與淺色版是同一套系統，不是換個底色
